# application/commands

## Overview
One factory per use case: `makeX(deps) -> async function`. Dependencies are injected ports plus an optional `clock`; two commands also take non-port deps: `makeReadAuditHistory` takes `{dbStore?, clock?}`, and `makeVerifyMfa` additionally takes `bumpVerifyAttempts` and `transitionToEnrolled` callbacks. Each command validates input, enforces state rules, and performs side effects. Every command except audit read writes a logbook row via `vaultLogbookEntry` on its success path.

## Interface
- `tokenize-aadhaar.ts`: `makeTokenizeAadhaar`, `TokenizeCommandError`. Strips spaces/dashes, requires 12 digits and `type === 'AADHAAR'`. `identityId` = UUID-shaped first 16 bytes of `sha256("1:<digits>")` (pepper version 1). Generates a DEK via `keyManager.generateDataKey("wrap:<identityId>")`, encrypts digits with AES-256-GCM (AAD `aadhaar-vault/v1|kv=<ver>|schema=1|identity=<id>`), then in ONE Mongo transaction (`vaultWriter.runWrite`) inserts identity (upsert, `$setOnInsert`), a new token (random UUID, wrapped DEK, iv, tag), and a `TOKENIZE` logbook row. Returns `{token, last4, tokenType, identityId, auditId, keyVersion}`; `auditId` = `requestId` if given else random UUID, and this same `auditId` is used as the logbook `LogEntry.id` (no `vaultlog_` prefix); all other commands use `mintVaultLogId`. Publishes `AadhaarTokenized` after commit. The same Aadhaar yields the same `identityId` but a new token each call. Known gap: re-tokenizing keeps the FIRST identity row (`$setOnInsert`) with its original `aad` (including `kv=<version>`), while each new token is encrypted with a freshly computed AAD and detokenize decrypts with the identity row's `aad`; if `KEY_VERSION` changes between the two tokenizations, the second token fails with `DECRYPTION_FAILED`.
- `request-detokenization.ts`: `makeRequestDetokenization`, `RequestDetokenizationCommandError(code,msg,httpStatus)`. Requires tokenId, factorId, actorId, reason; token, identity, and factor must exist; factor `status==='active'` and not expired. Creates a `pending` challenge (`operation:'detokenize'`, TTL default 300 s, pinned to token, identity, requiredFactorId, requestedBy). Logs `STEP_UP_REQUEST`; publishes `DetokenizationRequested`. Extra deps `ttlSeconds` and `newChallengeId`; `ttlSeconds <= 0` throws `INVALID_CONFIG` (500), a code not in `KNOWN_VAULT_CODES`.
- `approve-step-up-challenge.ts`: `makeApproveStepUpChallenge`, `ApproveStepUpChallengeCommandError`. Code must be 6 or 8 digits. The approver (`context.actorId`) must be the actor that requested the challenge and must own the factor (else `ACTOR_MISMATCH`, checked before any state change); the TOTP window is the fixed `APPROVE_TOTP_WINDOW` constant (1). Challenge must be `pending` (else `CHALLENGE_NOT_PENDING`) and unexpired (else best-effort `expire`, `CHALLENGE_EXPIRED`); factor must be active and unexpired. Opens the sealed secret (`openSecret`, context `mfa-factor:<id>`) and verifies the code. Wrong code: logs deny `STEP_UP_APPROVE`, publishes `StepUpChallengeFailed`, then makes a best-effort `fail` on the challenge and throws `CODE_MISMATCH`. Right code: logs allow row FIRST, then CAS `approve` (pending -> approved, stores `verifiedFactorId`, `auditId`); a lost race logs deny `CONCURRENT_TRANSITION` and throws `CHALLENGE_NOT_PENDING`. Publishes `StepUpChallengeApproved`.
- `detokenize-aadhaar.ts`: `makeDetokenizeAadhaar`, `DetokenizeCommandError`. Check order: challenge exists, not consumed, not expired, status `approved`, operation `detokenize`, `requestedBy === context.actorId`. Then atomic `consume` (approved -> consumed; loser gets `CHALLENGE_CONSUMED`). Then loads token and identity, unwraps the DEK (`UNWRAP_FAILED`), decrypts with the identity's stored AAD (`DECRYPTION_FAILED`), requires 12 digits (`INVALID_PAYLOAD`), writes `DETOKENIZE` logbook row via `dbStore.addLog`; if that write throws, the error propagates and plaintext is NOT returned. Publishes `DetokenizationCompleted`. Returns `{token, identityId, aadhaar, last4, auditId}` (note `auditId` is the requestId or `detok-...`, not the logbook row id).
- `enroll-mfa.ts`: `makeEnrollMfa`, `EnrollMfaCommandError`. Generates a TOTP secret (default SHA1, 8 digits, 30 s; a `period` other than 30 is stored but never honoured at verify time), seals it with `keyManager.sealSecret` under `mfa-factor:<uuid>`, inserts a factor (`active`, `PENDING_ENROLLMENT`), logs `MFA_ENROLL` (audit actor is `context.actorId`, not `cmd.actor`; the row has `identityId: null`), publishes `MfaEnrolled`. If the audit write fails the error is rethrown after the factor was inserted, leaving an orphan factor. Returns `{factorId, otpauthUri, factor}`; the otpauth URI contains the plaintext secret and is the only time it leaves the vault.
- `verify-mfa.ts`: `makeVerifyMfa`, `VerifyMfaCommandError`, result union `{valid:true,...} | {valid:false, reason}`. Default window 1. Increments `verifyAttempts` (best effort) before further checks; checks `expectedActor`, `status`, `expiresAt`, opens the secret, verifies the code, `markUsed`, logs `MFA_VERIFY`, and promotes `PENDING_ENROLLMENT` -> `ENROLLED` (logs `MFA_ENROLLMENT_VERIFIED`). Failures log deny `MFA_VERIFY` (plus `MFA_ENROLLMENT_FAILED` for pending factors) and publish `MfaVerificationFailed`; domain failures return rather than throw, but input validation and audit/event errors throw. Its audit rows have `identityId: null`. Only reachable through the `aadhaarVault.ts` facade (no HTTP route).
- `read-audit-history.ts`: `makeReadAuditHistory`, `ReadAuditHistoryCommandError`. Default limit 50, max 200 (clamped, not rejected). Fetches up to 4x limit rows with details prefix `vault:` from `dbStore.listLogsByDetailsPrefix`, filters in memory by `identityId`. Because MFA rows are written with `identityId: null`, they can never be returned by this command. Result can hold fewer rows than exist (scan window) and nothing is logged.

## Invariants
- Tokenize persists identity, token, and audit row atomically; if any fails nothing is committed and no event is published.
- Challenge state machine: `pending -> approved -> consumed`, or `pending -> expired|failed`; each transition is a compare-and-set on the previous status.
- Events are published (and awaited) after the persistence they describe. Storage success is independent of the publisher only because `InProcessEventPublisher.publish` never throws; a different `EventPublisher` that throws would turn a committed tokenize into an error response.
- Plaintext Aadhaar never appears in audit meta.

## Side Effects
- MongoDB writes through repositories and `vaultWriter`; `dbStore.addLog` writes to `logbook` (non-transactional for all but tokenize).
- `deps.events.publish` for each domain event.
- Key manager calls (generate/unwrap data key, seal/open secret).
